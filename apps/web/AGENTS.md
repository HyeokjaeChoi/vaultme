# apps/web

React Router v8 framework mode, `ssr: false`, prerendered, served by Workers Static Assets (ADR-0001, ADR-0013). Read `ARCHITECTURE.md`, ADR-0011, ADR-0012 and `DESIGN.md` before you change a screen.

- UI uses Tailwind utilities from `@vaultme/tokens` only (`theme.css`, `tokens.css`). No arbitrary values, raw colors or numeric styles (`scripts/check-repo-rules.sh` R2, R5, ESLint). A Figma size with no token goes in `app/app.css` as a `@utility` built from token values, with a removal note.
- Each file in `app/shared/ui` starts with `// Figma: <component> <node id>` (R6). Screens are route files in `app/routes`; copy comes from `@vaultme/i18n/web` (ko and en).
- A page ships no app JS unless its route sets `handle = { hydrate: true }` (`app/root.tsx`). The inline theme script (`app/shared/lib/theme.ts`) is the only script on static pages, and `scripts/finalize.ts` puts its sha256 in the CSP. Change the script and the hash follows at build time.
- The landing page is `app/routes/landing.tsx` (ko `/`, en `/en`, one component). Its head (canonical, hreflang, OG, JSON-LD) is JSX in the route (React 19 hoists it). `public/sitemap.xml` and `robots.txt` are hand-written with the production origin (`app/shared/lib/seo.ts`); `test/landing.test.tsx` checks they match the pages. The hero image is `AppMockup` (2x AVIF/WebP, the one `fetchpriority=high`). Store buttons stay inert until `app/shared/lib/stores.ts` gets real URLs (TODO(release)). The FAQ is native `<details>`.
- The viewer is `app/routes/address.tsx` (`/address`, `/en/address`, `hydrate: true`). The address lives in the URL fragment, a fragment-only change runs no route loader, so balances load in a hook (`app/shared/api/useBalances.ts`) through `@vaultme/api-client` with an install key made in the browser (`webSigner.ts`, ADR-0011). 
- Unknown paths answer a real 404 (ADR-0013). Do not add a SPA fallback.
 The viewer history list is `app/shared/ui/HistorySection.tsx`: 5 rows first, 더 보기 reveals 10 and asks for the next page, and every state keeps the skeleton height (`min-h-history-body`). Lighthouse covers the `/address` form only (the viewer needs an API); the history list is checked by `e2e/history.spec.ts` with fixtures. `@vaultme/history` and the API client load on the first read (`app/shared/api/useHistory.ts`).
- `test/build.test.ts` builds a fixture app (static index, hydrated route, 404). It guards the hydrate detection in `app/root.tsx`, which uses React Router's `UNSAFE_FrameworkContext`.
- Links and buttons are at least 44 px (`p-3 -m-3` or `min-w-touch-min`); the e2e spec checks every one.
- UI work follows the `vaultme-design-to-code` skill: light and dark comparison images at 375, 768 and 1280 in the PR.
- Fonts: `app/fonts.css` loads after first contentful paint (the inline script turns it on), so the Korean subsets (~270 KB) are not on the critical path. A `font-display: swap` stylesheet that loads before paint dropped mobile Lighthouse for the ko 404 to 92-96. Preloading a subset has the same effect, so there is none.
- PR previews are off (`web-preview.yml` removed, staging `preview_urls: false`) until a narrow-scope Cloudflare token exists: the `staging` environment has no branch policy, so a PR workflow would get the staging token. Cloudflare is checked before the staging deploy instead (`web-staging` job `gate`). Staging is served at `vaultme-staging.stack-line.dev` (custom domain in `wrangler.jsonc`).
- The transaction page is `app/routes/tx.tsx` (`/tx`, `/en/tx`, `hydrate: true`). The hash is in the fragment alone (a shared link has no address); `app/shared/api/useTransaction.ts` reads it with `readTransaction` from `@vaultme/api-client` (`eth_getTransactionByHash`, `eth_getTransactionReceipt`, the block time), same request numbering as `useBalances`. No history cache on the web (ADR-0011), so a row of the viewer list links to `/tx#<hash>` and passes its address in the router state (`{ from }`, memory only) for the back link; a direct link goes back to `/address`. A hash with no block yet is "not found". Same `data-boot` first-paint trick as `/address`. Checked by `e2e/tx.spec.ts` with fixtures; Lighthouse covers `/tx` with no hash (the invalid state), so the lazy API and wallet-core load is not measured there; `/tx` falls under the same viewer JS limit (153,600 B) as `/address`. A row passes its asset in the router state (`{ row }`), so an ETH row and a USDC row of one transaction each show their own move. The page also shows the transaction's internal transfers ("내부 이동", ADR-0015, #238): `app/shared/api/useInternalTransfers.ts` reads `readInternalTransfers` (`POST /v1/tx/internal`) beside the transaction, beside the transaction; the detail shows when the RPC reads are done and the section has its own loading rows, then list, nothing (hidden) or an error with retry (deadline 10 s). A section that turns out empty pulls the Etherscan link and footer up once (CLS measured 0.025 at most, `e2e/tx.spec.ts`). A failed internal read shows a notice and a retry in the section only. `app/shared/ui/InternalTransfers.tsx` draws it.
- Web Analytics (ADR-0012, #198): `scripts/finalize.ts` (not a route, so no screen code changes) adds the Cloudflare beacon `<script defer src=…/beacon.min.js data-cf-beacon>` before `</head>` of every built page only when the build sets `WEB_ANALYTICS_TOKEN` and `WEB_ENV` is not `production` (32 hex, public id; `web-staging.yml` sets the staging site's; local and CI `web` set none). The CSP already allows `static.cloudflareinsights.com` (script-src) and `cloudflareinsights.com` (connect-src). Measured on a built page with the real beacon: the RUM POST `location` has no fragment (`/tx`, not `/tx#0x…`), also for SPA route changes (`nt: routing-apis`); a hash-only change sends nothing. Cloudflare's docs do not state this, so re-check it if the beacon version changes (`js` field in the payload). Lighthouse runs on the build without the beacon (+10 KB gzip would exceed the 150 KB viewer budget; owner decision, #253); `e2e/analytics.spec.ts` checks the tag and CSP with a stub beacon.
